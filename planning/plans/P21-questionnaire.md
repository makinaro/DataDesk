**Q1. How does an exported notebook find its data?**
_Blocks: P21-01._

> **Recommendation (Claude):** Copy the data files next to the notebook.

> **Answer Q1:** — @spec-designer (Claude), 2026-10-03
>
> **Decision:** The first cell is a **parameters cell** with one path per input dataset (prefilled with the original paths) and the expected **content hashes**. The second cell verifies the hashes and stops with a clear message on a mismatch. Snapshots that came from a `select` are re-created by the same SQL in DuckDB (Python `duckdb`) inside the notebook. Bundling data is an **opt-in** export option with a size warning, and the export dialog lists which paths and data leave DataDesk.
>
> **Why:** Copying data by default duplicates possibly large and sensitive files into wherever the user saves notebooks, and a shared notebook would then carry the data along. Hash verification is what makes "re-runs to the same numbers" checkable rather than assumed.
>
> **Rejected:** copying data by default (privacy, size); absolute paths without a check (silent mismatches when the file changed).
>
> **Recommendation was:** overturned (parameters + hash check; bundling opt-in).
>
> **Consequences:** P21-01; `duckdb` is added to the notebook requirements (Q3).
>
> **Revisit if:** none expected.
>
> **Confidence:** High · **Needs maintainer:** no
>
> **Audit resolution (2026-10-03):** Expected hashes are over **canonical content** (sorted rows), not file bytes; paths are relative placeholders. DuckDB cells in user notebooks run with external access off, allowed directories, autoinstall off and `threads=1`. Generated cells encode names and SQL as `repr` literals and emit `text/plain` outputs only.
>
> **Audit resolution, round 2 (2026-10-03):** Bundling data is dropped from v1.0. Markdown is generated by code with no links or images; outputs export only on opt-in.

**Q2. Which export formats?**

> **Answer Q2:** — @spec-designer (Claude), 2026-10-03

> **Decision:** `.ipynb` by default, plus an optional `.py` in percent-cell format (readable in any editor, diff-friendly in git).

>
> **Rejected:** `.ipynb` only (hard to review and diff).
>
> **Recommendation was:** refined (optional `.py`).
>
> **Consequences:** P21-01.
>
> **Revisit if:** none expected.
>
> **Confidence:** High · **Needs maintainer:** no
>
> **Audit resolution (2026-10-03):** Commented-out risky cells are an explicit exception to NFR-15's "no dead cells".
>
> **Audit resolution, round 2 (2026-10-03):** Snapshots get a canonical `__row_id`; hashes cover ordered rows; agent loads become a code-owned `load` shim (Q-AJ2).
>
> **Audit resolution, round 3 (2026-10-03):** `__row_id` follows ingestion order and is dropped before frames reach the kernel; cells carry `metadata.datadesk` ids; restarts become reset cells (Q-AM2).

**Q3. How is the environment specified?**
_Blocks: P21-01._

> **Recommendation (Claude):** A `requirements.txt` with the package names.

> **Answer Q3:** — @spec-designer (Claude), 2026-10-03
>
> **Decision:** `requirements.txt` with **exact versions** matching the sandbox's packages (P13-01), plus `duckdb` and `altair`, and the Python version noted in the first Markdown cell. The re-run harness uses ~~`bench/env`~~ _(superseded: the sandbox, Q-AD1)_ (P12 Q5), whose lockfile is kept consistent with these pins.
>
> **Why:** Names without versions guarantee drift: a scikit-learn upgrade changes defaults and numbers. Exact pins are what make M-05 meaningful for someone else re-running the notebook a year later.
>
> **Rejected:** unpinned names (non-reproducible).
>
> **Recommendation was:** overturned (exact pins).
>
> **Consequences:** P21-01; ~~a CI check that `bench/env` and the sandbox pins agree~~ _(superseded, Q-AD1)_.
>
> **Revisit if:** some sandbox versions have no CPython wheels (pin the nearest and record the difference).
>
> **Confidence:** High · **Needs maintainer:** no
>
> **Audit resolution (2026-10-03):** Superseded: `requirements.txt` is for users only; harness re-runs happen **only in the compute sandbox**, never in `bench/env`, so there is no `bench/env` CI check (Q-AD1).
>
> **Audit resolution, round 2 (2026-10-03):** `requirements.txt` carries hashes; a CPython fixture-notebook CI job is the user-path evidence (Q-AJ1).
>
> **Audit resolution, round 3 (2026-10-03):** Hashes come from `resources/compute/pyodide.lock.json`, with a pin-agreement CI check; M-05b re-runs the gate notebooks in a no-network CPython child (Q-AM1).

**Q4. When does a re-run "match"?**
_Blocks: P21-02, M-05._

> **Recommendation (Claude):** All key-result numbers are identical.

> **Answer Q4:** — @spec-designer (Claude), 2026-10-03
>
> **Decision:** **Tolerance tiers** per key result: counts and categories exact; deterministic arithmetic (means, sums) relative 1e-9; linear algebra and statsmodels fits relative 1e-6; seeded ML and bootstrap results relative 1e-4. Each mismatch is reported with both values. M-05 counts a notebook as matching only if every key result is within its tier.
>
> **Why:** Pyodide (WebAssembly) and CPython use different maths libraries, so floating-point results differ in the last digits even with the same code and seeds. "Identical" would fail honest notebooks and make M-05 measure the platform instead of reproducibility. Tiers keep the bar strict where exactness is possible.
>
> **Rejected:** bitwise identity (false failures); a single loose tolerance (hides real drift in counts).
>
> **Recommendation was:** overturned (tiers).
>
> **Consequences:** P21-02; ~~the key-results schema carries a `kind`~~ _(superseded: the scorer derives it; tiers only for M-05b)_ per value so the tier can be chosen.
>
> **Revisit if:** some seeded algorithms differ beyond 1e-4 across platforms (then document them as platform-sensitive).
>
> **Confidence:** Medium · **Needs maintainer:** no
>
> **Audit resolution (2026-10-03):** The tier's `kind` is derived **by code** from the producing call, with the strictest tier as the default and an absolute floor per tier; the P12 scorer computes M-05 with one match rule (tolerance).
>
> **Audit resolution, round 2 (2026-10-03):** Tiers are superseded for M-05: exact equality within the same sandbox build, `env_mismatch` otherwise; tiers remain only for the manual CPython check (Q-AJ3).
>
> **Audit resolution, round 3 (2026-10-03):** M-05 counts key results with exact equality and a fixed hash seed; tiers apply only to M-05b; TS-vs-template metric parity test.

**Q5. Which sections does report v2 have?**
_Blocks: P21-03, EC21-2._

> **Recommendation (Claude):** Summary, methods, results, limitations.

> **Answer Q5:** — @spec-designer (Claude), 2026-10-03
>
> **Decision:** Headline (P10 Q1); key results (cited); methods (plan, design, tests and models, with versions); assumptions and how they were checked; results with charts; **limitations** (including every unresolved block-level finding, enforced by code, P19 Q6); method findings and their resolution; model cards (P17 Q5); lessons used (P20); provenance appendix (claim → output). A unit test checks every section is present.
>
> **Why:** "Summary, methods, results, limitations" leaves out what makes this product's reports trustworthy: provenance, findings and lessons. Each section maps to an existing schema, so the report is assembled mostly by code.
>
> **Rejected:** the four-section report (drops the trust features).
>
> **Recommendation was:** refined (full section list tied to schemas).
>
> **Consequences:** P21-03; the `report-format` skill v2.
>
> **Revisit if:** reports get too long for casual readers (then collapse the appendices by default).
>
> **Confidence:** High · **Needs maintainer:** no
>
> **Audit resolution (2026-10-03):** Report v2 is **assembled by code** with agent prose slots (Q-AD6) and adds sampling, weights, exploratory labels, derived lineage, the fan chart and refit status, and late `studyDesign` changes; empty sections say "n/a"; code-generated numbers are excluded from M-04/M-19; a v1 → v2 schema migration.
>
> **Audit resolution, round 2 (2026-10-03):** Method findings, model cards, run status and the provenance appendix are restored; the scorer checks each section against its source record.

**Q6. Where does the analysis view live?**
_Blocks: P21-04._

> **Recommendation (Claude):** A new window.

> **Answer Q6:** — @spec-designer (Claude), 2026-10-03
>
> **Decision:** **Inside the existing Results area as an "Analysis" tab** (closable like other result tabs, Phase 9), with sections for plan, executions, derived datasets, models, findings and lessons used. There is no new window.
>
> **Why:** A new window doubles the security work (every `BrowserWindow` must be hardened, CLAUDE.md rule 2) and breaks the two layouts the Phase 9 work settled. A tab reuses existing patterns and keyboard handling.
>
> **Rejected:** a new window (security surface, layout fragmentation).
>
> **Recommendation was:** overturned (a tab, not a window).
>
> **Consequences:** P21-04; component and e2e tests.
>
> **Revisit if:** none expected.
>
> **Confidence:** High · **Needs maintainer:** no
>
> **Audit resolution (2026-10-03):** Untrusted text renders as text; new IPC channels have zod schemas and payload caps.

**Q7. What does compare mode show for analysis tasks?**
_Blocks: P21-05._

> **Recommendation (Claude):** Both answers side by side.

> **Answer Q7:** — @spec-designer (Claude), 2026-10-03
>
> **Decision:** Answers side by side **plus** a key-results diff table (values per provider, highlighting disagreements beyond tolerance), method findings per lane, provenance badges, cost, time and execution count. Where both providers ran the same benchmark task, the score is shown too.
>
> **Why:** Two prose answers side by side hide where the providers actually disagree. The diff table makes disagreements obvious, which is the point of comparing.
>
> **Rejected:** answers only (disagreements hidden in prose).
>
> **Recommendation was:** refined (diff table and trust signals).
>
> **Consequences:** P21-05.
>
> **Revisit if:** none expected.
>
> **Confidence:** High · **Needs maintainer:** no
>
> **Audit resolution (2026-10-03):** Superseded: no benchmark scores or accuracy in the app and no automatic disagreement diff; values sit side by side with their method (Q-AD4). D-022 is amended by a D-NNN.
